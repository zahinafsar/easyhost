# EasyHost Project Memory

## Current state (2026-09-29)
- Layout: client/ (Vite dashboard), server/ (Hono API), cli/ (`ezhst`, npm package ezhst), marketing/ (static HTML+CSS), infra/postgres (shared TLS-enabled Postgres), scripts/start.mjs
- Env: a single root `.env` both locally and on the VPS (no `.env.production`; templates `.env.example` and `.env.production.example`). No fallbacks anywhere; server validates via server/src/lib/env.ts, client via client/src/lib/env.ts. `npm start` refuses empty or `<PLACEHOLDER>` values
- Fixed values are code constants: LIMITS (10 projects, 5 apps and 5 schedules per project, 1 bucket/database/email sender per project, 20 emails/day, 1 concurrent build), API port 48710, EMAIL_DOMAIN easyhost.fun, bucket easyhost-deploys, docker network easyhost, MinIO user easyhost
- Local ports: API 48710, dashboard 51730, shared postgres 127.0.0.1:54329, minio 127.0.0.1:19000/19001
- MinIO images: pgsty/minio + pgsty/mc (official images are no longer public)

## Production (VPS luggora, 65.181.123.115)
- Nginx Proxy Manager owns 80/443 and terminates TLS; user chose to keep NPM in front (rejected Caddy as front door)
- Caddy removed (2026-09-29): NPM routes everything. Platform hosts -> `easyhost-api:48710` (API serves marketing, dashboard SPA, www redirect by Host in prod), storage -> `easyhost-minio:9000`, `*.easyhost.fun` wildcard proxy host with advanced config `set $server "eh-app-$1"` from host regex
- NPM must be connected to docker network `easyhost` (manual one-time step) and use docker resolver (resolvers.conf) so container names resolve per request
- Existing custom-domain proxy hosts made before this pointed at easyhost-caddy; new ones forward to `eh-app-<slug>:3000`
- Local dev: no app routing at all; `ROUTING` deploy step enum still exists in Prisma/CLI but the server no longer sets it
- Shared postgres publishes 5432 directly; TLS cert for db.easyhost.fun issued in NPM and mounted read-only (NPM_LETSENCRYPT_DIR, POSTGRES_CERT_NAME), reloaded every 6h
- Custom app domains: in production, the API creates an NPM certificate then proxy host via NPM API (dedicated NPM user with "Created Items Only" recommended); local development skips NPM

## Features
- Projects: preserved existing root App rows as project workspaces. Child apps use App.parentProjectId; root apps remain visible when appEnabled=true. appName separates the app display name from the project name. Existing IDs, deployment URLs, service references and histories are preserved without backfills. New projects start appEnabled=false. `/api/projects` lists/creates/renames/deletes projects; `/api/apps` is scoped by X-Project-ID with max 5 enabled apps including an existing root app. Creation locks the project row to enforce the cap. App deletion keeps shared project services, including for existing root apps; project deletion removes all children and schedules. Pending deployments block deletion. Prisma schema updated and client generated only; user must run `npm run prisma -- migrate dev --name project_apps_schedules` in server and commit the generated migration before production startup.
- Settings is project-scoped, not account-scoped. It renames only the project display name (the deployment slug/URL remains stable) and exposes full project deletion. Deletion cleans up the container, routes, images, deployment artifacts, domains, MinIO bucket/credentials/files, Postgres database, email data, and API keys; deleting the last project returns the dashboard to its create-project state.
- `/` redirects to `/apps`, which lists the selected project’s apps with create and per-app detail screens. Sidebar adds Schedules. Project switching uses projectsQuery and appIds for deep links; app/schedule queries include selected project IDs.
- Deploy: any Node.js app with package.json. Lockfile selects npm/pnpm/yarn/bun; build script runs only when present; scripts.start or a Node entry file is detected, with Next.js fallback and custom overrides. HTTP apps must listen on 0.0.0.0 and PORT=3000. CLI uses --project plus --app, links may save appId; deploy can create an app when none exists. Postgres-backed build queue remains.
- Storage: S3 compatible, no custom storage API (v1 storage removed). Each bucket gets a MinIO service account (access/secret key on Bucket row) with an inline policy scoped to that bucket, created/rotated/removed by shelling out to `mc` (MC_HOST_eh env). API image copies mc from pgsty/mc; local dev needs mc on PATH. S3 endpoint = STORAGE_PUBLIC_URL, path-style, region us-east-1, bucket name = minioName eh-<id>. All files public by URL. Dashboard file browser still works via root MinIO client
- Databases: one Postgres container hosts platform easyhost and customer db_<hex> + role u_<hex> each, plus <db>_shadow for prisma migrate dev; console + table editor run as the owner role. Provisioning and Prisma both use DATABASE_URL (explicit port and TLS sslmode required); USERDB_URL and USERDB_PASSWORD removed. Every startup writes HBA rules that block customer access to easyhost/postgres/template1 and require TLS for TCP connections, including on existing volumes. The postgres_data volume is retained; old userdb_data must be backed up/restored before restarting an existing two-instance installation (README instructions). No services restarted or tests run during consolidation (2026-10-01)
- VPS consolidation completed successfully on 2026-10-01. Customer databases, shadow databases, roles, passwords, ownership and privileges were moved into the shared Postgres instance. The one-time updater, migration guards and migration documentation were removed afterward. The VPS retains its rollback backup directory and original customer data volume outside the repository
- Removed the stale `CADDY_ADMIN_URL` entry from the local `.env` and `.env.production`; routing uses Nginx Proxy Manager and the `NPM_*` variables
- Email: Resend remains the provider. Sender addresses <username>@easyhost.fun (reserved names blocked); send API requires `from`. Free sending is limited to 20 successful sends per project over a rolling 24 hours. Resend daily/monthly quota and rate-limit errors return HTTP 503 with the exact message `Serice temprarily paused due to over usage` through both send endpoints. Other provider errors remain HTTP 502. No tests run for this change (2026-10-11).
- Schedules (2026-10-11): max 5 per project, intervalMinutes 1–43200, method/headers/body, pause/resume/edit/delete through dashboard and CLI. Worker polls every 10s, leases each job for 60s with a unique token, caps each request at 30s, pins public DNS results (private IPs blocked), refuses redirects, skips missed intervals, retains 100 runs and exposes latest 10. No tests run; static type checks only. No database migration applied.

## Admin (2026-09-30)
- Lives inside the dashboard at `/admin` (client/src/pages/admin.tsx, standalone route outside AppShell; tabs Health, Analytics, Usage, Users). Only `User.role = ADMIN` (existing enum, no migration). There is no UI to grant admin: the user runs the one-off shell snippet in `seed-admin.txt` (repo root) on the VPS, which upserts a verified ADMIN inside the running api container. User rejected boot-time seeding from env vars and any npm script or source file for it
- API: server/src/routes/admin.ts behind server/src/middleware/require-admin.ts (`/api/admin/health|analytics|usage|users`, `POST /api/admin/users/:id/impersonate`)
- Impersonation: admin gets a 2h JWT for the target with an `impersonatorId` claim, replacing the auth cookie; `getCurrentUser` exposes `impersonatorId`; impersonated sessions are rejected by requireAdmin; AppShell shows a red banner and `POST /api/auth/stop-impersonating` restores the admin session. Starts are only written to the API log (user chose no audit table)
- Analytics are computed from existing tables (signups, projects, deployments, emails per day); no page view tracking. Usage shows live container memory/CPU (docker stats), database size and emails per project; bucket sizes are not measured
- Project deletion lives in server/src/lib/delete-project.ts (`deleteProject`), shared by the user route and `DELETE /api/admin/projects/:id`. The admin route also emails the owner (`sendProjectDeletedEmail`); a failed email does not undo the deletion (`emailSent: false`). Admin Usage tab has per-project Impersonate owner and Delete buttons
- Schedules page (client/src/pages/schedules.tsx) renders schedules as a single Card+Table (name/status, request, interval, next run, actions); no per-schedule run history list in the UI.
- Project members (2026-11-04): ProjectMember + ProjectInvite models (migration project_members). Owner = root App.userId, role Owner or Member only, limits stay per project (LIMITS.projectMembers = 10 members + pending invites). findProjectApp(projectId, idOrSlug) no longer filters by userId; requireProject checks owner or member. New child apps get the project owner's userId. Invite accept (POST /api/invites/:token/accept) requires the logged-in email to match and marks the user verified. Dashboard: /members page, /invite/:token page, Settings is owner only. Login/register pass ?redirect through. CLI: members list|invite|revoke|remove|leave, accept-invite
- AI apps / Builder (2026-11-04): App.kind AI (migration ai_apps) with aiStatus/aiProgress/aiError/aiAuthSecret and AiMessage chat rows. Slug is the exact name (unique, not reserved), counts against the 5 apps per project limit. Files in MinIO bucket easyhost-ai/<appId>/ (bucket created on demand), pushed into container eh-app-<slug> from image easyhost/ai-runtime (server/ai-runtime: node 22, preinstalled hono, @hono/node-server, pg, bcryptjs, jose, zod, @aws-sdk/client-s3 in /srv/node_modules, code in /srv/app, node --watch server.js, npm cache volume easyhost-npm-cache). Env injected: app env + PORT + AUTH_SECRET + DATABASE_URL (project db, auto-created by run_sql). Generation: AI SDK ToolLoopAgent + @ai-sdk/google gemini-4-argon, key GOOGLE_GENERATIVE_AI_API_KEY (required), 40 steps max, background job, GENERATING reset to FAILED on boot. Limits: aiPromptsPerDay 30 per project, aiFiles 200, aiFileBytes 256 KB. Payments later via Lemon Squeezy; everything free for now. Dashboard /builder and /builder/:id only (AI builder was removed from the CLI)
- ai-runtime image is built by the `ai-runtime` service in docker-compose.yml and docker-compose.prod.yml (build ./server/ai-runtime, image easyhost/ai-runtime, entrypoint true, restart no); prod api depends_on it with service_completed_successfully. No separate npm script
- AI app npm packages: AI uses the install_packages tool (server/src/lib/ai-apps.ts installAiPackages): docker exec `npm install <pkgs>` in /srv/app (3 min timeout, output returned to the AI), then the container's package.json is copied back to MinIO and the container restarts once. Package names are validated. Writing package.json only restarts the container when `dependencies` changed. start.sh still reinstalls on container start (shared npm cache). No native build tools in the image
- AI builder v2 (2026-11-04): starter template lives in server/ai-template (now just a static EasyHost welcome page with build instructions plus lib/db, auth, storage, email helpers; no demo login or tables) (copied into the api image by server/Dockerfile, loaded by server/src/lib/ai-template.ts). provisionAiServices creates the project database, bucket (createProjectBucket in lib/minio.ts, shared with the storage route), email sender (username from slug) and an `ai-<slug>` API key stored in the app env as EASYHOST_API_KEY. Container env also gets S3_*, EMAIL_FROM, EASYHOST_EMAIL_URL. Dev: env.isProduction false means published 127.0.0.1 port (aiPreviewUrl), localhost URLs rewritten to host.docker.internal. Agent records steps (App.aiSteps live, AiMessage.steps per reply; migration ai_steps). Workspace UI is full screen with chat, step timeline, device preview and code view; Builder home is a prompt-first hero
- AI builder live steps: ai-agent uses agent.stream() and turns stream parts into steps (text steps, tool steps with status running/done/error, title, detail = file content or SQL streamed from tool-input-delta, output = SQL rows, npm or log output). In-memory hub server/src/lib/ai-live.ts (single API process); SSE GET /api/ai-apps/:id/events sends a snapshot then step upserts and done. requireProject also accepts ?projectId= for EventSource. Steps are saved on AiMessage.steps (content = joined text), App.aiSteps holds a throttled snapshot for failures. Workspace opens the EventSource only while aiStatus is GENERATING
- AI app resources (2026-11-04): no provisioning at creation, and the AI never asks. App.aiDatabaseId / aiBucketId (migration ai_app_resources) link the app's database and bucket. run_sql auto-connects the project database (creates it if missing, links it, restarts the app). connect_storage tool does the same for the project bucket, setup_email creates sender + ai-<slug> API key. Each request starts with a "Connected services" line. Database password reset restarts AI apps linked to that database
- AI builder flow (2026-11-04): for a new app or big feature the AI calls pausing tools (no execute) ask_questions (max 3, 2-4 options each), propose_plan (summary + max 6 items), choose_theme; small edits go straight to code. Cards are steps of type questions/plan/theme saved on AiMessage.steps; POST /api/ai-apps/:id/respond {stepId, answers | approve | theme} answers the latest reply, adds a user message and resumes. 9 predefined themes in server/src/lib/ai-themes.ts (easyhost, slate, ocean, forest, sunset, grape, rose, midnight, mono: colors, radius, Google font); choosing one sets App.aiTheme (migration ai_theme) and writes public/theme.css with CSS variables. Each request includes a Theme line. Generated apps must use only theme.css variables, Lucide icons via unpkg lucide@1.68.0 UMD, no emojis, no unrequested features
